Why pinright

Docs plus a verdict, in fewer tokens than docs alone

Docs MCP servers return documentation for a library. They do not check the version the agent pins, and they do not see the install. To measure that kind of server we ran pinright's own server with its security layer off: docs for the version asked, no verdict. It is not another product.

What the agent sees

Docs for the version to move to, with the verdict on top

When the agent asks for docs of a vulnerable version, get-docs names the same-line fix, documents that version, and fences the third-party text so the agent treats it as data.

The get-docs answer is the example from docs/how-it-works.md, shortened.

How it works

One npm package, four ways in

  • 01 · Docs

    Docs for the version you pin

    README, docs and type definitions published at that version, the repo at its release tag, the project's llms.txt. No index service in between.

  • 02 · Verdict

    A verdict per dependency

    Advisories from OSV and deps.dev, malware records, deprecation, lookalike and nonexistent names. The fix stays on your release line when one exists.

  • 03 · Hook

    A pre-install hook

    Checks installs and manifest writes before they run, in Claude Code, Cursor, VS Code, Codex, Gemini CLI and Windsurf.

  • 04 · CI

    A GitHub Action

    Whole-tree audit of lockfiles and workflows, with SARIF for code scanning and annotations on the pull request.

Also a CLI for people: pinright check npm axios@1.7.9, pinright audit ., pinright upgrade, pinright doctor. Ecosystems: npm, PyPI, Cargo, Go, RubyGems, NuGet, Maven and Gradle, Composer, GitHub Actions.

Privacy

Runs on your machine

  • No account, no key, no telemetry.
  • No install scripts: installing it runs no code.
  • Sends package names and versions to public services (deps.dev, OSV, registries, jsDelivr, GitHub). Never your source code, files or environment.
  • A guardrail, not a sandbox: it reads commands and files; it does not contain what an allowed package does.
