Tu agente de programación fija versiones de memoria. pinright las revisa antes.

Documentación de cada biblioteca para la versión exacta que instala tu agente, y un veredicto sobre cada dependencia que agrega: avisos de seguridad conocidos, registros de malware, nombres parecidos y paquetes que no existen.

Tu equipo, o para probarlo. Escribe archivos del proyecto que subes al repositorio.

$ npx -y pinright init

Solo tú, en cada proyecto. Instalación global, configuración de usuario.

$ npm i -g pinright && pinright init --user
Guía de instalación Agregar a Cursor Instalar en VS Code GitHub

Node 20.9 o posterior. Sin cuenta, sin clave, sin telemetría. Los botones de Cursor y VS Code agregan solo el servidor MCP; ejecuta init en el proyecto para tener el hook. 16 clientes, seis con hook.

El problema

Los agentes sacan las versiones de memoria, o de herramientas de documentación que no las revisan

Cuando un agente escribe un manifiesto, la versión sale de sus datos de entrenamiento, que suelen ir años detrás del registro, o de un servidor MCP de documentación, que devuelve docs y no contrasta la versión con los avisos de seguridad. Ninguno de los dos mira la versión que fija el agente.

  • De memoria

    40% a 42% de las versiones fijadas tenían un aviso

    Tres modelos de Claude sin herramientas, 12 tareas: unas 30 alertas en todo el árbol por proyecto, con versiones como axios@1.7.9 (33 avisos) y pillow@11.0.0 (86).

  • Desde un servidor MCP de docs

    Docs actuales, y aun así versiones vulnerables

    La documentación de la versión actual bajó las alertas a 0,3 a 3,5 por proyecto. En 4 de 72 ejecuciones el agente igual fijó un next o next-auth vulnerable, como next@15.5.0 con 32 avisos.

  • Con pinright

    0% de las versiones fijadas tenían un aviso

    Cada dependencia recibe un veredicto antes de que el agente la fije, con un arreglo en la misma línea de versiones, y el hook revisa la instalación misma. Las 0,3 alertas que quedan por proyecto vienen de nuxt, que no tiene arreglo publicado.

Medimos el caso del servidor MCP de docs con el propio servidor de pinright, con la capa de seguridad apagada; no es otro producto. Con una shell, los agentes buscaron las versiones por su cuenta y todos los brazos terminaron en las mismas 6 alertas. El método y las salvedades están en la página de evidencia.

Una instalación, de principio a fin

Qué hace pinright cuando tu agente instala un paquete

Tu agente ejecutó npm install {lodash@4.17.20}, una versión de memoria con {5 avisos conocidos}. El hook de pinright la {bloqueó} antes de que se ejecutara y propuso {4.18.1} en la misma línea de versiones. Después, {get-docs} sirvió la documentación de esa versión.

Por qué pinright

Docs más un veredicto, con menos tokens que solo docs

Los servidores MCP de documentación devuelven la documentación de una biblioteca. No revisan la versión que fija el agente y no ven la instalación. Para medir ese tipo de servidor ejecutamos el propio servidor de pinright con su capa de seguridad apagada: documentación de la versión pedida, sin veredicto. No es otro producto.

Lo que ve el agente

La documentación de la versión a la que hay que moverse, con el veredicto arriba

Cuando el agente pide la documentación de una versión vulnerable, get-docs nombra el arreglo en la misma línea, documenta esa versión y encierra el texto de terceros en un delimitador para que el agente lo trate como datos.

La respuesta de get-docs es el ejemplo de docs/how-it-works.md, recortado. La herramienta responde en inglés.

Cómo funciona

Un paquete de npm, cuatro formas de usarlo

  • 01 · Docs

    Documentación de la versión que fijas

    README, documentación y definiciones de tipos publicadas en esa versión, el repositorio en su tag de release y el llms.txt del proyecto. Sin un servicio de índice en el medio.

  • 02 · Veredicto

    Un veredicto por dependencia

    Avisos de seguridad de OSV y deps.dev, registros de malware, paquetes deprecados, nombres parecidos y nombres que no existen. El arreglo se queda en tu línea de versiones cuando hay uno.

  • 03 · Hook

    Un hook de preinstalación

    Revisa instalaciones y escrituras de manifiestos antes de que se ejecuten, en Claude Code, Cursor, VS Code, Codex, Gemini CLI y Windsurf.

  • 04 · CI

    Una GitHub Action

    Auditoría de lockfiles y workflows en todo el árbol, con SARIF para code scanning y anotaciones en el pull request.

También hay una CLI para personas: pinright check npm axios@1.7.9, pinright audit ., pinright upgrade, pinright doctor. Ecosistemas: npm, PyPI, Cargo, Go, RubyGems, NuGet, Maven y Gradle, Composer, GitHub Actions.

Privacidad

Corre en tu máquina

  • Sin cuenta, sin clave, sin telemetría.
  • Sin scripts de instalación: instalarlo no ejecuta código.
  • Envía nombres y versiones de paquetes a servicios públicos (deps.dev, OSV, registros, jsDelivr, GitHub). Nunca tu código fuente, tus archivos ni tu entorno.
  • Es una barrera de protección y no aísla procesos: lee comandos y archivos, y no contiene lo que haga un paquete permitido.
